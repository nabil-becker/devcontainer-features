# ADR-0078: A node issues certificates itself by default, with the CA key in OpenBao, else an ssh-agent, else a file

| | |
|---|---|
| **Status** | accepted |
| **Date** | 2026-11-23 |
| **Deciders** | the Operator; proposed by the host |

## Context

ADR-0069 says a trust domain's certificates come from an OpenBao PKI, and a hub's OpenBao is
unsealed by hand after each start. While planning the hub on Kubernetes the Operator found OpenBao
a strong dependency: the devhost's own OpenBao listens only on the container's loopback, holds the
Operator's personal and the backs' secrets (the wrong blast radius for a hub's CA), and is up only
while that devhost runs. The Operator asked for a lightweight default, as a SQL Server
installation can run "localdb" until someone says "use my existing server".

N5a already built a small built-in issuer for peer-to-peer nodes: a CA kept as a file in the
state volume and limited to its own domain. A spike
([docs/spikes/2026-11-23-ssh-agent-ca.md](../spikes/2026-11-23-ssh-agent-ca.md)) showed that an
ssh-agent holding an ed25519 key can sign a root CA and node certificates, that two SLIM nodes link
over mutual TLS with them, and that a certificate from another key is refused. It also found that a
URI-name constraint on the built-in CA makes SLIM reject every certificate it signs, so the
constraint keeps the DNS rule only; lock two of ADR-0069 still checks the domain.

## Decision

1. **A node issues its domain's certificates itself by default.** No OpenBao is needed and nothing
   is unsealed; the node restarts on its own and backs its roster up to its volume.
2. **The CA key comes from the first of three places that is configured**:
   1. an OpenBao PKI (`node.issuer.openbao`: a URL and an AppRole), as ADR-0069;
   2. an ssh-agent (`node.issuer.ssh_agent`: a socket and a key fingerprint), the node building
      each certificate and asking the agent to sign it; the key must be ed25519 and the agent
      should hold nothing else;
   3. a file in the node's volume, mode 600, as a last resort that `check` warns about.
3. **The root is generated by the hub or its agent** and can be exported to be taken offline.
4. `facilitator node issuer migrate` moves a built-in node onto OpenBao later; spokes keep their
   certificates until renewal and need no re-join.
5. Only the CA key moves; SLIM still reads each node's own TLS key from a file.
6. This amends ADR-0069 decisions 1 and 2: OpenBao is the preferred issuer, not the only one, and
   the "unseal by hand" step applies only when OpenBao is configured.

## Options considered

### Option 1: built-in issuer by default, OpenBao or an ssh-agent when configured (chosen)

Removes the hard dependency, keeps the stronger stores available, and the Kubernetes hub becomes
one StatefulSet and its volume.

### Option 2: a separate OpenBao beside the hub

Right blast radius, but a second stateful service to run and unseal for every hub.

### Option 3: point the hub at an existing OpenBao

Only sensible for a shared OpenBao run as a service, which does not exist today.

### Option 4: keep ADR-0069 as it stands

Rejected by the Operator as too heavy a dependency for a default.

## Consequences

- Anyone who can read a built-in hub's volume can mint certificates for its domain; for a shared
  intranet hub OpenBao stays the recommendation.
- An ssh-agent that goes away stops issuing and renewing; existing certificates stay valid until
  they expire. A hub whose agent is often away (a sleeping laptop) may want longer certificates.
- In Kubernetes the agent socket must reach the pod (a sidecar or a forwarded socket); that is fine
  for a lab hub, and production should use OpenBao or a cloud key service.
- Only ed25519 agent keys work as they are; RSA and ECDSA hash first and FIDO keys cannot be used.
- The ssh-agent tier is built after the spike's result, in the hub slice.
