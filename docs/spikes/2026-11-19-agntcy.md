# Spike: the AGNTCY components run by hand (2026-11-19)

Backlog id `facilitator-agntcy-spike`; slice 0 of `docs/proposals/facilitator-agent.md` (sections 4.8 and
8). Who it serves: the Operator, through the host, and the engineer who will install the `facilitator`
Feature. Nothing was built: no Feature, no install script. Everything below was run in this devhost
(x86_64, 8 CPUs, 15 GB RAM, Docker 29, Python 3.13) on 2026-11-19, with every daemon on loopback and every
download in its own empty directory, verified before it ran. Where something was read from docs and not run,
it says **from docs**.

## Result in one paragraph

Both AGNTCY components run here with **no Docker**, on loopback, light: the directory daemon takes about
145 MB and the SLIM node about 20 MB. A Python client sent a message from one process to another and ran a
3-member MLS group through the node. Four things differ from what the proposal assumed: the SLIM node is
not a release asset (it is inside `slimctl`); `dirctl` publishes no checksum file; the directory daemon
binds two ports to all interfaces by default; and `slim-mcp` on PyPI is pinned to a `slim-bindings` that
does not talk to the current node. None stops the design.

## 1. Agent Directory (`dir`, `dirctl`)

**Obtain and verify.** Latest release `v1.9.1` (2026-11-18, previous `v1.9.0` 2026-11-11), Apache-2.0.
Assets (single static binaries, no archive): `dirctl-linux-amd64` (198 MB), `dirctl-linux-arm64` (184 MB),
`dirctl-darwin-amd64`, `dirctl-darwin-arm64`, `dirctl-windows-amd64` and a `.zip`, plus
`dirctl-v1.9.1.intoto.jsonl`. **There is no checksum file and no `.sig` or sigstore bundle per asset.**
What exists: the SHA-256 that the GitHub release API returns per asset (`digest`), and one SLSA v1
provenance file whose `subject` list holds the SHA-256 of every binary. Both agreed with the downloaded
`dirctl-linux-amd64` (`adf2cbf7...b3c4`) and `dirctl-linux-arm64` (`cd998d00...c701`). I did not verify the
provenance's own signature (no `slsa-verifier` or `cosign` here), so the check is "download equals the
API digest equals the provenance subject". `dirctl version` prints `v1.9.1 (a8b704fa)`.

**Run.** `dirctl daemon start --data-dir <folder>` (also `daemon stop|status|config init|policy`). One
process: API server, reconciler, OCI store, libp2p routing, HTTP gateway. No Docker, no Zot, no PostgreSQL.

| Measure | Seen |
|---|---|
| Listening on start | `127.0.0.1:8888` gRPC API; `127.0.0.1:5555` local OCI registry; **`0.0.0.0:8999` libp2p routing**; **`*:8889` HTTP gateway** |
| Fix | in `<data-dir>/daemon.config.yaml`: `routing.listen_address: "/ip4/127.0.0.1/tcp/8999"`, `http_gateway.listen_address: "127.0.0.1:8889"`. After that `ss` shows only loopback. Env overrides exist: `DIRECTORY_DAEMON_SERVER_LISTEN_ADDRESS`, `..._ROUTING_LISTEN_ADDRESS` and others |
| State | everything under `--data-dir` (default `~/.agntcy/dir`): `daemon.config.yaml` (written on first start), `dir.db` (SQLite), `store/` (OCI layout), `routing/` (Badger), `node.key`, `daemon.pid`. 328 KB when empty |
| Memory (RSS) | 142 MB just after start, 150 MB after a few pushes |
| Start-up | first start 1.3 s (key generation, first config); warm start: API listening after 0.19 s |
| Background | reconcilers wake every minute (indexer, signature, identity, metrics, regsync) |

On every start the daemon publishes one record of its own (`org.agntcy/directory`, an Agent Skill usage
guide, schema 1.0.0), so a search of an empty directory returns one record.

**Push, pull, search.** An OASF record for "jester" (`example.invalid/jester`, version `v0.1.0`, schema
`1.1.0`, skill `language_processing/language_generation/story_generation` id 10306, domain
`media_and_entertainment/content_creation` id 1302, one locator) pushed with `dirctl push jester.json`,
returned the CID `baeareib2jwvwtlmaqqkjqsbrtqpo775zese64cutahkkar6kadcgsqtm7u`, and `dirctl pull <cid>` gave the
record back unchanged. `dirctl search --name "example.invalid/*"` and `--skill language_processing/...`
both found it; `dirctl info <cid>` shows name, version and schema. Natural-language search
(`dirctl search "a jester who tells jokes"`) refuses until `dirctl init` sets up an OASF extractor (not tried).
Signing (`dirctl sign`) needs a Sigstore OIDC identity or a key; not tried.

**What it taught.**

- **Push validates against a remote schema server by default** (`https://schema.oasf.outshift.com`, which
  served schema 1.1.0 and server 2.0.0). A bad locator was refused with a precise message (`locators[0].urls`
  required, not `url`); the schema's skill names changed between 1.0.0 (`natural_language_processing/...`)
  and 1.1.0 (`language_processing/...`). With `policy.operations: []` in the config the daemon accepted a
  record with an invented skill and never contacted the schema server: **the default needs internet, the
  offline setting accepts anything**. The Feature must choose and say so.
- The record identity is its CID (content hash), so the same record pushed twice is one record, and a
  change is a new CID: that is the "digest" the proposal's lineage can cite.
- `dirctl` as a client defaults to `0.0.0.0:8888` (`--server-addr`); it needs `127.0.0.1:8888` said.
- The binary is large (198 MB): a download per container build, worth a cache volume.

## 2. SLIM

**Obtain and verify.** Latest GitHub release `slimctl-v3.4.6` (2026-10-20). **There is no node binary among
the release assets** (the `slim-v3.4.6` release has none; the README names Docker, Cargo or Helm for the
node). The node is inside `slimctl`: `slimctl slim start --config <yaml>`. Assets per platform: `gnu` and
`musl` tarballs for linux amd64 and arm64 (also macOS, Windows), each with `.sigstore.json` and
`.intoto.jsonl`; **no checksum file** (the API `digest` stands in, and matched the download).
`slimctl-linux-amd64-gnu.tar.gz` 21.7 MB, binary 58.9 MB, `slimctl version` says `3.4.6`, git `aa932ea`.
I verified the sigstore bundles for **amd64 and arm64** with the Python `sigstore` 4.5.1 package in a
throwaway venv: `sigstore verify identity --cert-identity
https://github.com/agntcy/slim/.github/workflows/release-rust.yaml@refs/heads/main --cert-oidc-issuer
https://token.actions.githubusercontent.com` printed OK for both. The container image
`ghcr.io/agntcy/slim` has tags `3.4.6` and `3.5.0` (= `latest`), both linux amd64 and arm64; **`3.5.0` has
a git tag and an image but no GitHub release yet.** I did not pull or verify the image (no Docker needed).

**Run.** A config (mine, in the spike scripts) with one dataplane server on `127.0.0.1:46357`, `tls:
insecure: true`, and `auth: {type: basic, username, password: ${env:SLIM_PASSWORD}}`. The node logs
`Auth is enabled without TLS. This is not recommended.` (loopback only, so accepted). **Authentication
used: basic auth for the transport**, secret from an environment variable; a client with a wrong password
was refused (`link negotiation error ... connection send error`). Separately, each app has an identity: the
spike used the **shared-secret** mode (at least 32 bytes) and the node does not see it.

| Measure | Seen |
|---|---|
| Port | `127.0.0.1:46357` (one) |
| Memory (RSS) | 18.9 MB idle, 25.6 MB after the p2p and group runs; 12 threads (2 cores configured) |
| Start-up | listening after 80 ms |
| State | none on disk; the node is stateless (a restart drops sessions) |

**Python client.** `slim-bindings`: PyPI latest is `3.3.9` (2026-10-27), although `slim_bindings.get_version()`
reports `3.4.6` (the PyPI number lags the project's tags: GitHub has `slim-bindings-v3.4.6`, PyPI stops at 3.3.9).
Wheels are `py3-none` so one wheel serves every Python 3.10+: **manylinux_2_28 and musllinux_1_2 for x86_64
and aarch64**, macOS x86_64 and arm64, Windows amd64 and arm64; 24 MB each. `3.3.4` is yanked. **It can be
pinned with hashes**: `pip install --require-hashes -r req.txt` with
`slim-bindings==3.3.9 --hash=sha256:440e5426...e3c4 (x86_64) --hash=sha256:7e8d2f40...a348 (aarch64)`
installed with no dependencies at all.

- **Point to point:** receiver `agntcy/spike/alice`, sender `agntcy/spike/bob`, separate processes, MLS on:
  session set up in 22 ms, two messages answered, round trips 50 and 92 ms.
- **Group (3 members, MLS):** moderator creates the session on a topic name, invites two members
  (`invite_async`, then `wait_async`), `participants_list` shows all three, a publish reached both; after
  `remove_async` of one, that member got `session closed` and the other still received the next message.
- **`get_message_async(timeout)`** is the blocking receive with a timeout: exactly the primitive the
  facilitator's `receive` tool needs ("nothing yet" on timeout, a message otherwise).
- Gotchas: use the blocking `service.create_app_with_secret(...)`; the `_async` variant panics with "there is
  no reactor running" in this release. Names are always three parts (`org/namespace/app`). A client must also
  `subscribe` its own name before others can reach it. Blocking and `*_async` method pairs exist for most calls.

**What it taught.** SLIM is lighter than the directory by a factor of seven and needs no files; names are
hierarchical, sessions are explicit objects (open, invite, remove, close) rather than "write to a file", and
membership changes rekey the group. The Feature must hold the basic-auth secret and the shared secret
(OpenBao, as the proposal says) and hand them to clients by environment.

## 3. A2A and MCP over SLIM

- **`slim-mcp` 0.2.3** (PyPI, 2026-06-24, classifier "Alpha", Apache-2.0; the repository was pushed on
  2026-11-19 but its version is still 0.2.3). It pins **`slim-bindings~=1.4` and `mcp==1.26.0`**, Python
  3.11+. Installed as is (bindings 1.4.1) it fails against the 3.4.6 node at `subscribe`:
  `connection not found: 0`. With `slim-bindings` 3.3.9 forced in (no dependency check) it got as far as one
  line: `SessionConfig(enable_mls=False)` no longer exists in 3.x (`mls_settings=None` replaces it). With that
  **one-line change in the installed copy** an MCP server and client, both through a second no-auth node on
  loopback, did `initialize`, `list_tools` and a `call_tool` of `receive` and got the text back over SLIM.
  So it can carry an MCP tool call; it takes a patched or forked `slim-mcp` (or an upstream release that moves
  to bindings 3.x) and a decision on `mcp` pinned at exactly 1.26.0.
- **`slima2a` 0.9.3** (A2A over SLIM, repository `agntcy/slim-a2a-python`, pushed 2026-11-19): requires
  `slim-bindings>=3.3.6,<4` and `a2a-sdk==1.2.3`; it is current. Read, not run.

## 4. T1: does an agent keep calling a blocking `receive`?

Tool: a stdio MCP server (`FastMCP`, one tool `receive`) that sleeps N seconds and returns "nothing yet", and
on the third call a message. Command: `claude -p --model haiku --max-turns 12 --output-format json
--strict-mcp-config --mcp-config <file> --allowedTools mcp__recv__receive --tools ""`, with the prompt "Loop:
call the receive tool; when you get a message (a text starting with MESSAGE), answer it in one sentence, then
call receive again; stop after the message." Claude Code 2.1.311.

| Block per call | Calls | Turns | Wall time | Cost | Result |
|---|---|---|---|---|---|
| 5 s | 3 | 4 | 21 s | $0.0011 | looped, answered the message, stopped |
| 60 s | 3 | 4 | 183 s | $0.0004 | the same |
| 300 s | 2 (message from call 1 on) | 3 | 603 s | $0.0003 | both 300 s calls completed; no timeout; it called again once, then stopped |

- **It loops**, and it did not give up on "nothing yet". With the message on every call from the first, it
  called once more and treated the repeat as a repeat, which is a prompt matter for the facilitator's text.
- **A 300 s blocking call did not time out** (twice, back to back). The CLI limit is therefore above 300 s here;
  I did not search for the ceiling. The Feature can use blocks of 60 s or longer.
- **Cost is negligible** (total about $0.002 for four runs); `max-turns 12` was never reached.
- Caveat: one model (Haiku), one prompt, `-p` mode only; interactive mode was not run.

## 5. AGNTCY Identity (from docs only)

`agntcy/identity`, Apache-2.0. **It now states a version**: releases `v0.0.25` and `v0.0.26` (2026-09-29), a
`v1.0.0-beta.1` tag exists; still pre-1.0. The issuer CLI is a release binary (`identity_linux_amd64` and
`arm64`, with `_checksums.txt`, a `.sig` per binary, a signing key and an in-toto provenance file). **The Node
backend still needs Docker**: `launch_node.sh` or `make start_node` run Docker Compose with PostgreSQL
(`0.0.0.0:5432`) and the node (`0.0.0.0:4000`); a Helm chart is the other route. So it stays opt-in and
needs Docker-in-Docker where the host allows it.

## Requirements for the facilitator Feature

**Ports (all must bind to loopback)**

- SLIM node `127.0.0.1:46357`.
- Directory: `127.0.0.1:8888` (API), `127.0.0.1:5555` (OCI), and the two that bind to all interfaces by default
  and must be changed in the config: `8999` (libp2p) and `8889` (HTTP gateway).
- `check` must name the owner of a port in use; four directory ports, not one.

**Memory and time:** directory about 150 MB RSS, SLIM node about 20 to 25 MB; start 0.2 s (warm) to 1.3 s
and 0.08 s. About 175 MB for both, idle. The directory wakes every minute.

**State paths (under `/var/lib/devcontainer-features/facilitator/`)**

- directory: pass `--data-dir <volume>/dir`; it holds `dir.db`, `store/`, `routing/`, `node.key`,
  `daemon.config.yaml`, `daemon.pid`. Back up `node.key` with the rest.
- SLIM node: none (stateless); config and its basic-auth secret live outside the node's folder.
- Python client venv: one folder, rebuilt from the pinned wheel.

**Python and wheels:** Python 3.10 or newer (3.13 here); `slim-bindings` is one `py3-none` wheel per platform,
manylinux_2_28 or musllinux_1_2, x86_64 and aarch64 both exist; hash-pinned `pip` works with
`--require-hashes`. Pin `slim-bindings==3.3.9` (reports node 3.4.6) and use the blocking `create_app_with_secret`.

**What must be pinned**

- `dirctl` v1.9.1: both linux binaries by SHA-256. The directory publishes no checksum file; the Feature
  keeps the SHA-256 in its own table (checked against the release API and the provenance subjects at pin
  time), which fits the download helper of ADR-0034.
- `slimctl` v3.4.6: gnu tarballs for amd64 and arm64 by SHA-256, with the sigstore verification done at pin
  time (needs the `sigstore` tool, or cosign, on the maintainer's side; the Feature can only check the hash).
- `slim-bindings` 3.3.9: two wheel hashes. Node and bindings versions move together; PyPI numbering lags.
- `slim-mcp` 0.2.3 cannot be used as published (needs a patch or fork; see section 3); `mcp` 1.26.0 exactly.
- The OASF schema server: the daemon's default policy calls it on push; choose online or `operations: []`.

**What needs Docker:** nothing in the first version. Only AGNTCY Identity's node (opt-in, slice 7).

**Other**

- Node auth: basic over loopback plain text is accepted with a warning; the secret comes from an environment
  variable; app identity uses a shared secret of 32 bytes or more.
- The record's schema version is a moving target (1.0.0 and 1.1.0 names differ); register-engine stores OASF
  1.1.0, the directory's own record is 1.0.0.
- `slimctl 3.5.0` exists as an image but has no release; the proposal's pin stays at 3.4.6 until one appears.
